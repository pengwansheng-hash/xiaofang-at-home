# 架构说明

## 1. 技术目标

首版优先稳定、可纠偏、可解释，不追求“最聪明”。高风险照护信息必须结构化确认，容易失控的能力必须被边界化。

## 2. 端云职责

| 层 | 职责 | 首版建议 |
| --- | --- | --- |
| 老人端 Android | 录音/播报、待办展示与确认、本地提醒、本地缓存 | Kotlin 原生，不做重模型本地推理 |
| 子女端轻应用 | 绑定、提醒设置、老人信息维护、查看结论与异常 | H5 / 微信内打开优先 |
| 应用服务层 | 鉴权、家庭绑定、提醒计划、消息路由、日志 | REST API + 推送服务 |
| AI 服务层 | ASR、对话、摘要、记忆抽取、风险初筛 | 模块化拆分，厂商可替换 |
| 数据层 | 档案、提醒、事件、摘要、日志 | 结构化数据库优先，对象存储只留必要冷数据 |

## 2.1 老人端实现路线

- 正式技术栈：Kotlin + Jetpack Compose
- 页面导航：Navigation Compose
- 本地状态与业务层：ViewModel + StateFlow
- 本地持久化：Room + DataStore
- 后台任务：WorkManager
- 依赖注入：Hilt
- 媒体能力：MediaRecorder / AudioRecord、TTS、通知与闹钟能力

不采用的路线：
- 不以 Next.js / H5 / WebView 包壳作为正式老人端交付方案
- 不把 v0 原型代码直接并入安卓工程

采用原因：
- 提醒、通知、音频、权限、后台限制和低端机适配都更依赖原生能力
- Compose 更适合高保真复刻 v0 的移动端界面气质

## 2.2 v0 原型迁移策略

原型来源：
- `F:\临时文件\大模型落地\小芳在家\b_Xd3kyLO6CQg`

迁移原则：
- 把 v0 当作视觉母版和页面结构来源，而不是工程底座
- 优先复用页面模块划分、组件命名语义、配色和交互顺序
- 所有 mock 数据通过 Android 端本地假数据仓库重新实现
- 所有 `console.log`、页面跳转和 Web 事件逻辑都按原生交互重写

首批 Compose 映射建议：
- `AppHeader` -> `XfTopBar`
- `BottomTabBar` -> `SeniorBottomNavigation`
- `ReminderCard` -> `HighlightReminderCard`
- `TaskItem` -> `TodoListItem`
- `VoiceButton` -> `HoldToTalkButton`
- `ContactCard` -> `EmergencyContactCard`

## 2.3 子女端实现路线
- 首版子女端采用 `Next.js App Router + TypeScript` 的移动 H5 工程
- 运行形态优先面向微信内打开，同时兼容普通 Android / iPhone 浏览器
- 页面壳层采用顶部摘要 + 单栏卡片流 + 底部轻导航的轻应用结构
- 骨架阶段先用本地 mock 数据跑通绑定、今日状态、提醒设置、老人信息、异常页 5 个核心页面
- 登录与服务端鉴权先留接口边界，骨架阶段不引入复杂账户体系
- 端内状态先用 React Context + `localStorage` 保存绑定上下文和提醒计划，后续再替换为服务端同步层
- 绑定上下文至少保留老人姓名、绑定码、绑定时间、绑定方式和当前浏览器中的家庭视角，保证绑定页、今日状态页和异常页读取的是同一份上下文
- 今日状态页与提醒设置页共用同一份端内提醒状态，避免“提醒已改、首页还没变”的双份状态漂移
- 异常页首版同样基于这份端内状态派生：先根据绑定状态、提醒待同步状态、待确认提醒和关键联系人生成异常卡，再在后续替换为服务端异常摘要
- 老人信息页首版也复用同一套端内状态思路，在浏览器本地保存称呼风格、常聊话题、禁忌词、作息和联系人，后续再替换为服务端资料同步

## 3. 提醒系统

- 主策略：本地提醒为主，云端消息兜底
- 本地提醒负责：固定任务、弱网可用、端侧执行
- 云端消息负责：计划同步、补发提醒、异常升级、家属消息
- 风险边界：不把后台常驻作为前提，不让语音直接写正式计划

当前代码状态：
- 已建立 `ReminderScheduler` 原生接口，并接入 `AlarmManager + BroadcastReceiver + NotificationCompat`
- 已在 Android 原型中打通“新增提醒 / 编辑提醒 / 删除提醒 -> 写入本地持久化 -> 同步本地通知调度”的最小闭环
- 已支持通知点击携带 `reminderId` 回流到原生详情页
- 已接入麦克风权限申请、`MediaRecorder` 录音、本地 `m4a` 文件保存、最近录音回放、`SpeechRecognizer` 转写与陪伴页状态回写
- 已补充精确提醒调度、重启后提醒恢复和单次提醒不过期重排的稳定性处理
- 当前仍未支持更细粒度的计划管理和更复杂的多周规则

## 4. 薄记忆架构

| 层 | 内容 | 是否进入上下文 | 存储 |
| --- | --- | --- | --- |
| 短时会话层 | 最近 6-12 轮对话 | 是 | 缓存 / 数据库 |
| 核心档案层 | 称呼、关系、偏好、禁忌词、常聊话题 | 是 | 结构化表 |
| 事件记忆层 | 吃药、腿酸、睡不好、打电话等 | 按需 top-k | 事件表 |
| 摘要层 | 近 3 天摘要、当日结论 | 是，少量 | 摘要表 |
| 原始日志层 | 完整转写、音频、调试日志 | 默认不进入 | 对象存储 / 冷数据 |

## 5. 推进边界

- 首版不做全量历史自由检索
- `memory_inference` 不直接触发关键动作
- 高风险字段需要 `source`、`confidence`、`last_verified_at`
- 低端 Android 优先保障通知、权限和基本性能，不上复杂常驻策略

## 6. 技术阶段

| 阶段 | 目标 | 验收标准 |
| --- | --- | --- |
| T0 原型 | 录音、播报、本地提醒、待办页跑通 | 开发者可连续完成 3 次提醒与确认 |
| T1 双端闭环 | 绑定、今日结论、提醒设置、异常提醒 | 1 个家庭连续使用 7 天 |
| T2 稳定性版 | 热词、二次确认、日志、低端机调优 | 10 个家庭内测无阻断问题 |
| T3 试点版 | 规则调优、成本优化、机型扩大 | 20-50 家庭试点可用 |

## 7. 当前代码落地顺序

1. 搭建 `android-senior-app` Compose 原生骨架
2. 用 mock 数据高保真还原 v0 首页、今日待办页、提醒确认页、语音陪伴页
3. 接入本地提醒、通知和基础本地存储
4. 再补新增提醒、联系人和偏好设置
5. 最后再接服务端与 AI 能力

## 8. 当前原生实现状态

- `SeniorAppViewModel`：统一管理昵称、沟通风格、提醒同步提示和录音状态
- `SeniorPreferencesStore`：当前已接入 `SharedPreferences` 持久化
- `ReminderRepository`：当前已接入 `SharedPreferences` 持久化提醒列表
- `ReminderScheduler`：当前已接入 `AlarmManager` 本地提醒调度、通知接收器与重启恢复接收器
- `VoiceCapability`：当前已接入系统 `TextToSpeech` 播报、`MediaRecorder` 录音、本地语音文件保存、最近录音回放、`SpeechRecognizer` 转写与提醒草稿回写
