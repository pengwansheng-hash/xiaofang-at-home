# 小芳在家 PRD

## 1. 产品概述

- 产品名称：小芳在家
- 当前定位：面向独居或半独居老人的 AI 照护代理
- 产品形态：老人端 Android App + 子女端轻应用
- 当前版本：V1.1 立项基线
- 核心目标：围绕提醒、轻陪伴、薄记忆、今日结论和异常回传，完成最小闭环并进入 14 天家庭试用验证
- 老人端实现路线：安卓原生 App，不采用 WebView 包壳作为正式交付方案

## 2. 目标用户

### 2.1 老人端用户
- 年龄：60-80 岁
- 设备：常用 Android 手机
- 特征：数字能力偏弱，希望操作简单，不喜欢被命令或被监视
- 核心诉求：被惦记、提醒不烦、步骤少、出问题时能快速联系家属

### 2.2 子女端用户
- 年龄：30-50 岁
- 使用场景：工作忙，低频打开
- 核心诉求：一眼知道父母今天情况，异常时能快速介入，不被噪音打扰

## 3. 当前版本必须解决的问题

- 老人缺少温和、可持续的提醒和确认机制
- 陪伴对话缺少熟悉感，每次像重新开始
- 子女难以低频掌握父母当天的关键状态
- 异常信息缺少结构化回传和升级策略

## 4. V1.1 MVP 边界

### 4.1 当前版本必须做
- 老人端 Android App
- 子女端轻应用
- 家庭绑定
- 语音交互
- 待办录入与查看
- 提醒确认与稍后提醒
- 薄记忆
- 今日结论
- 异常提醒
- 轻量鼓励反馈，如留言、点赞、红包占位

### 4.2 下一版本再做
- 更完整的试点扩容
- 成本优化、机型扩展、推送与规则调优
- 更丰富的鼓励机制和服务化能力
- 子女端轻应用与服务端联调闭环深化

### 4.3 当前明确不做
- 在线问诊
- 病历解析
- 全量聊天记录中心
- 复杂趋势图
- 机构后台
- 全本地大模型
- 远场自由唤醒
- 重支付体系

## 5. 产品原则

- 老人感受到的是被惦记，而不是被监管
- 子女端是低频配置和结果查看工具，不是高频运营后台
- 高风险照护信息必须结构化确认，不依赖模型自由猜测
- 语音只能生成待办草稿，不能直接成为正式照护计划
- 老人端正式交付以原生 Android 体验和系统能力稳定性优先，前端原型只作为设计与实现参考

## 6. 核心功能

### 6.1 老人端
- 首页：问候、今日待办进度、说话入口、提醒卡片
- 待办录入页：录入吃药、喝水、吃饭、运动、休息、复诊等事项
- 今日待办页：查看未完成/已完成待办，支持补确认和稍后提醒；列表中需区分当前待处理与后续待处理
- 对话页：语音聊天、字幕、AI 回复；长按录音按钮开始录音，松开后本地保存语音片段并回写状态提示，支持回放最近一次录音，并支持将语音转成提醒草稿后再确认保存
- 提醒确认页：我已完成 / 稍后提醒 / 需要帮忙
- 偏好设置页：称呼、话题、禁忌词、提醒风格
- 一键联系页：联系家属或紧急联系人，列表项可直接拉起系统拨号
- 绑定码展示页：老人端生成并展示绑定码，支持刷新和真实复制到系统剪贴板后发给子女端
- 求助确认页：在提醒确认页、语音陪伴页和联系人页进入，支持说明求助原因、优先联系家属并一键拨号

### 6.3 当前实现策略补充
- 已有 v0 生成的老人端 Web 前端原型，可作为视觉、页面结构和组件拆分参考
- Android 原生实现必须优先复用 v0 的页面层级、文案语气、卡片组织和核心交互顺序
- 不直接复用 v0 的 Next.js 工程代码作为正式老人端代码
- 偏好设置首版先支持称呼、沟通风格、常聊话题、禁忌词的本地保存，后续再与子女端和服务端同步
- 子女端首版采用 `Next.js App Router + TypeScript` 的移动 H5 工程，优先适配微信内打开，其次兼容普通手机浏览器
- 子女端骨架阶段先跑通绑定、今日状态、提醒设置、老人信息与异常页 5 个核心页面，暂不接入复杂登录体系

### 6.2 子女端
- 绑定页：输入绑定码或扫码
- 绑定页：输入绑定码或扫码；绑定成功后展示老人姓名、绑定码、绑定时间、绑定方式和下一步入口，不让用户只看到一句“已成功”
- 今日状态页：今日结论、完成情况、风险等级、是否需要介入；当子女端本地调整提醒计划后，今日状态页应立即反映最新提醒数量、最近一条提醒、是否存在待同步项，以及当前需要介入的异常数量
- 提醒设置页：新增、编辑、删除提醒计划；首版先支持本地增删改并保留在当前浏览器，后续再接老人端同步
- 老人信息页：基础信息、偏好、禁忌词、重要联系人；首版先支持在当前浏览器本地修改称呼风格、常聊话题、禁忌词、作息描述和重要联系人
- 异常页：异常摘要、建议动作、一键联系；首版先根据绑定状态、本地提醒计划和待同步状态生成异常卡，未接服务端前也能提示“先绑定 / 先同步 / 今晚最好联系一下”
- 鼓励页：留言、点赞、红包占位

## 7. 双端职责划分

| 模块 | 老人端职责 | 子女端职责 |
| --- | --- | --- |
| 提醒与待办 | 查看今日待办、确认完成、稍后提醒、极简补录 | 新增/编辑提醒计划、查看每日提醒总览 |
| 资料与记忆 | 确认高风险信息、补充偏好 | 输入老人基础信息、常聊话题、禁忌词、重要联系人 |
| 状态回传 | 日常回应与执行 | 查看今日结论、查看异常摘要 |
| 情感反馈 | 接收问候与鼓励 | 留言、点赞、红包占位 |

## 8. 关键流程

### 8.1 默认绑定流程
1. 老人先安装 Android App
2. 完成极简初始设置：称呼、1 个提醒、1 个家属联系方式
3. 老人端先单独可用
4. 老人端生成绑定码或二维码
5. 子女通过轻应用输入绑定码或扫码完成绑定
6. 子女端绑定成功后，先在本地保留当前家庭上下文、绑定方式和“待服务端校验”状态，再进入今日状态页
7. 子女补充关系、提醒计划、通知偏好和老人基础信息
8. 老人端可在联系人/资料页再次打开绑定码页，便于重新绑定或更换子女端设备

### 8.2 待办录入与确认
1. 老人端手动录入简单待办
2. 子女端录入更完整的计划配置
3. 语音转结构化草稿
4. 老人或子女确认后，草稿写入正式 `care_plan`
5. 端侧同步本地提醒；若为每周提醒，需明确具体星期几

### 8.3 异常升级
- 默认不上报：单次未回应、单次轻微不适、模型不确定推测
- 可升级上报：连续漏药、连续多次无回应、明确不适重复出现、老人主动要求联系家属

### 8.4 需要帮忙流程
1. 老人在提醒确认页、语音陪伴页或联系人页点击“需要帮忙”
2. 进入求助确认页，看到默认原因、建议联系人和拨号入口
3. 老人可直接拨打家属或紧急联系人，也可先返回
4. 首版先在端侧完成求助说明和拨号动作，后续再补家属端异常回传

## 9. 验收指标

| 假设 | 验证方式 | 建议阈值 |
| --- | --- | --- |
| 老人愿意持续回应 | 10 个家庭试用 14 天 | 7 日平均响应率 >= 60% |
| 子女愿意查看今日结论 | 打开率与推送点击 | 日查看率 >= 40%，周留存 >= 50% |
| 提醒计划准确可执行 | 提醒命中 + 回访 | 关键待办完成率稳定 |
| 异常提醒有价值 | 告警命中与误报核对 | 高风险命中率高且误报可接受 |

## 10. 当前阶段结论

V1.1 不是做“功能越多越好”的陪护产品，而是围绕提醒、熟悉感和家属放心感建立最小闭环。当前优先级是把提醒、薄记忆和结论回传做稳，再决定是否进入公开试用或扩展能力。

## 2026-04-12 语音陪伴页交互改版补充
- 老人端语音陪伴页从“工具按钮页”调整为“语音/文字双通道聊天页”。
- 长按话筒开始听写，松开后立即结束本次语音输入，并将系统识别出的文字作为老人消息发给小芳。
- 小芳的回复必须同时以文字气泡显示；当自动播报开关为开启状态时，同步调用系统 TTS 主动朗读回复。
- 语音陪伴页不再保留“回放录音、语音转写、试听播报、联系家人”这组独立工具按钮，避免老人把对话页误认成工具页。
- 语音陪伴页右上角改为喇叭开关：关闭时仅显示文字回复，开启时回复同时自动播报。
- 语音陪伴页底部保留两个主输入方式：文字输入框 + 发送按钮，以及长按说话主按钮。
- 若语音识别失败或没有拿到有效文本，必须在页面上给出清楚反馈，而不是无响应。
## 2026-04-12 老人端提醒与资料页交互补充
- 新增提醒 / 编辑提醒页中的“提醒时间”需替换为更适合老人选择的 24 小时制时间控件，避免当前控件难以精确选择小时和分钟。
- “重复规则”中的每天 / 每周 / 单次三个选项应采用整行三等分布局，单个选项更长、更易点按。
- 今日提醒页移除底部“陪伴提示”模块，底部导航中的“首页”入口必须可正常返回首页。
- 家人与资料页中的常用联系人卡片需要支持直接删除；常聊话题和尽量避免的话题输入框高度提升一倍；保存资料后需给出可见的成功反馈，2 秒后自动消失，同时允许手动关闭。

## 2026-04-12 老人端沟通风格人格化补充
- 家人与资料页中的沟通风格选项从“温和陪伴 / 简洁提醒”升级为“耐心细腻型 / 自信成熟型”。
- “耐心细腻型”对应冯雪风格：语言温柔、耐心、细腻、带轻微幽默和亲昵感，适合轻松陪伴、慢节奏提醒与情绪安抚。
- “自信成熟型”对应陈雅风格：语言简洁、直接、理性、稳定，带适度引导感，适合明确提醒、事务梳理与坚定关怀。
- 程序内必须为两种风格各自保存独立的人格提示词（system prompt），不能只改按钮名称。
- 陪伴页回复逻辑必须根据当前风格切换不同的小芳人格：同一问题在两种风格下的回话语气、节奏和措辞应明显不同。
- 为兼容已保存的本地资料，旧版本的 `Warm / Brief` 存档值需要自动兼容映射到新的两种人格风格。
